Connectors and data sync are experimental features under active development. The API and behavior may change.
:::

Connectors pull data from external services and sync it into your connected databases. This lets you query third-party data with SQL alongside your own data.

:::note[Vocabulary]
A **connector** is code: the thing that knows how to check a credential and read entities — Mako's built-ins below, or one your workspace ships under `connectors/<slug>/`. A **connection** is a credential your workspace configured with a connector. Connections come in two kinds: a _database_ connection (BigQuery, Postgres, MongoDB, …) that Mako queries and that flows write to, and a _source_ connection (a Stripe key, a Close account, …) that flows read from. The agent tools follow the same words: `list_connectors` is the catalog of code, `list_connections` is what is configured, of both kinds.
:::

## How It Works

1. **Configure** — Add a source connection with API credentials and select which entities to sync
2. **Map** — Choose a destination database and table naming convention
3. **Sync** — Connectors fetch data in chunks with cursor-based pagination
4. **Resume** — If a sync fails, it resumes from the last saved cursor (idempotent upserts)

## Probing a Connection Live

A connector is defined once — check, entities, read — and a flow is only one of the things that can drive a connection made with it. The **live probe** runs a configured source connection, with the credential Mako holds, directly against its platform: the credential check, then one bounded page of an entity, written nowhere. Use it to confirm a new key works, to see the real shape of an entity before writing a flow, or to look at a platform's data before a flow lands it in the warehouse.

Three surfaces, one implementation, so they cannot drift on what "bounded", "read-only" and "no credential in the result" mean:

| Surface                                  | How                                                                                                                                                  |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| MCP (any agent, or the in-product agent) | `probe_connection({ connectionId, entity?, limit?, fields?, since? })` — ids from `list_connections`, entity names from `inspect_connection`         |
| CLI                                      | `mako connection probe <id\|name> [--entity <name>] [--limit <n>] [--fields a,b] [--since <iso>] [--json]`                                           |
| REST                                     | `POST /api/workspaces/:wid/connections/sources/:id/probe` (legacy alias: `POST /api/workspaces/:wid/connectors/:id/probe`) with the same body fields |

The result carries the check outcome, then `entity.records`, `entity.schema` (declared field types), `entity.hasMore` (further pages exist on the platform), `entity.truncated` (the page held more than `limit`) and the connector's own log lines. Limits: at most `limit` records (default 20, max 200) from a single API page, and a 90-second budget for the whole probe — a connection whose connector is [workspace-authored](/guides/building-connectors/) runs in a sandbox, so its first probe can take tens of seconds. Every string value of the connection's config is scrubbed from the result, including from a vendor error that would echo the key back.

Nothing is written: no destination table, no sync cursor. The one side effect is the same one **Test connection** has — a workspace source connection's last-check mark, which is what moves its connector to _verified_.

## Calling a Service Live

Workflows and agents can also call a source connection's service directly, through Mako, without ever seeing its key: Close, Stripe, Wise, and **Custom API** connections. Mako adds the stored credential, keeps every request under the connection's address, and removes the credential from what comes back.

**Custom API** is any HTTP or GraphQL API with a stored key. It is never synced; it is only called. Set its address, a credential type (bearer token, API key in a header or in the query string, basic auth, a Google service account, or none), and optionally headers sent with every request (for example `Notion-Version`). Those headers are not secret: anyone who can see the connection sees them, and the credential's own header and transport headers (`Authorization`, `Cookie`, `Host`, …) cannot be set there. With **GraphQL API** on, only a query POSTed to the endpoint is a read; a mutation, and any GET, is a write.

**Test** checks the credential, not just that the service answers. It sends a GET to the optional **Test path** under the address (with GraphQL on, `{ __typename }` instead), reports a refused credential on HTTP 401/403 and any other error status as a failure, and otherwise passes on a 2xx. For APIs that answer 200 with the error in the body, set **Test expects** to a JSON field and the value it must have, as `path=value` (for example `ok=true` or `data.status=active`); a miss fails Test and reports the field, its actual value and the API's error, and a value that is not `path=value` fails Test instead of being skipped. Slack (`slack.com`) is checked for `ok=true` by default, on `/auth.test` unless a Test path is set.

A **Google service account** connection stores the service account's JSON key file, encrypted, and sends a short-lived Google token with each request; the key itself never leaves Mako. Pick **access token** for Google APIs; it is sent only to an address under `https://*.googleapis.com` (set scopes, default `cloud-platform`; for Google Workspace APIs, optionally a user to act as, which needs domain-wide delegation), or **ID token** for your own service behind Google sign-in (Cloud Run, Cloud Functions, IAP). An ID token's audience defaults to the address's origin, which is what Cloud Run expects; for IAP, set it to the OAuth client ID. The service account needs the role that lets it call the service, for example `roles/run.invoker` on a Cloud Run service.

**Managers** configure a connection: its creator, whoever a manager adds, and the workspace owner. The address, the credential type and the headers can only be changed in the app, never with an API key or by an agent.

The connection's **Access** tab decides who may call it:

- **Live reads**: off for every connection until a manager turns them on. Then anyone in the workspace (workflows and agents included) may read: GET and HEAD, a GraphQL query, a Close search or a Close POST read as GET.
- **Writers**: who may write (POST, PUT, PATCH, DELETE). Add people, or **All deployed workflows** (deployed workflows share one identity, so they are allowed together). Viewers and agents never write, and a person who left the workspace can no longer call it at all.
- **Refused attempts**: every write, allowed or not, is logged; refused ones are listed with who tried, so a manager can allow that person or the deployed workflows (an agent's attempt cannot be allowed).

From a workflow, see [Workflows](/workflows/#calling-a-service-through-a-connection); from an MCP client, `call_connection` reads only.

## Building Custom Connectors

See the [Building Connectors](/guides/building-connectors/) guide for implementing new connectors.

Each connector extends `BaseConnector` and implements:

```typescript
class MyConnector extends BaseConnector {
  // Declare available entities and their BigQuery layout hints
  getEntityMetadata(): EntityMetadata[];

  // Fetch a chunk of data with resumable state (cursor-based)
  fetchEntityChunk(options: ResumableFetchOptions): Promise<FetchState>;

  // Test connectivity
  testConnection(): Promise<ConnectionTestResult>;

  // Validate configuration
  validateConfig(): { valid: boolean; errors: string[] };
}
```

## Configuration

Source connections are configured per-workspace through the UI or API. Credentials are encrypted at rest using the `ENCRYPTION_KEY` environment variable.
